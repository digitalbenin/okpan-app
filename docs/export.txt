Static Website Export Feature - Implementation Guide
Context
The application is an Electron-based database connection tool that manages collections of cultural objects from different institutions. The system has two distinct frontend components:

Main Application - Electron app with full database access for data management and editing
Website Frontend - SvelteKit-based preview/export system located in website folder
Currently, the website frontend serves dual purposes:

Preview Mode: Runs inside the Electron app with direct SQLite database access for real-time preview
Export Mode: Needs to generate a truly static website (HTML files) that can be hosted independently
Current Architecture
Website Structure
The website folder (website) contains:

SvelteKit application with routes for browsing objects
Components for filtering, search, grid display, pagination
Database utilities (dbUtils.js) that query SQLite directly
Search utilities (searchUtils.js) for client-side filtering
Image utilities for displaying media assets
Data Model
Objects have the following relationships:

Belongs to ONE institution (with name, country, location, website)
Has MANY research fields (many-to-many relationship)
Has MANY media files (images with multiple format sizes: sm, md, lg, original)
Has research data (designations and categories)
Current Filtering System
The main page (+page.svelte) supports:

Text search across object names and descriptions
Institution filter (single select dropdown)
Research field filters (multiple checkboxes)
All filtering happens client-side on loaded data
Results are paginated (12 items per page)
Media Management
Each project has a dedicated media folder containing all uploaded files
Images are stored in multiple sizes/formats (thumbnails, medium, large, original)
Format metadata is stored in database as JSON: { sm: "path/to/small.jpg", md: "path/to/medium.jpg", ... }
Aim
Create a complete static website export system that:

Generates truly static HTML files using SvelteKit's adapter-static for all pages (homepage, individual object pages, etc.)
Maintains dual-mode operation - the same codebase must work for both preview (database) and export (static JSON)
Preserves all existing functionality - search, filtering, pagination must work identically in static export
Bundles all required assets - media files, search index, metadata in a standalone package
Enables offline operation - exported site should work without internet connection

Theoretical Implementation Steps

Phase 1: Data Export Architecture
Step 1.1: Design Unified Data Structure
Create a comprehensive JSON schema that embeds all relationships within object records to eliminate the need for JOIN operations at runtime. The structure should include:

Objects array: Each object contains all its related data embedded (not referenced by ID)

Object properties (id, name, description)
Full institution object nested (not just institution_id)
Array of research field objects (not just IDs)
Array of media objects with all format paths
Research data object containing designations and categories arrays
Filter metadata: Separate arrays for UI filter components

Institutions list with object counts
Research fields list with object counts
Export metadata: Information about the export

Export timestamp
Total object count
Project metadata
This unified structure allows all queries (filter by institution, search by research field, etc.) to work on a single in-memory dataset without needing separate lookups.

Step 1.2: Create Export Service Module
Build a new service module (src/lib/services/websiteExport.js) that orchestrates the entire export process. This service should:

Accept projectId and output path as parameters
Coordinate multiple sub-processes (data generation, media copying, build execution)
Handle errors gracefully with detailed logging
Clean up temporary files after successful export (if needed)
Step 1.3: Implement Data Generation Logic
Create a function that queries the database and generates the unified JSON file. The logic should:

Query Strategy:

Use SQL JOINs with GROUP_CONCAT to fetch objects with related data in minimal queries
Fetch media separately and organize by object_id in a map
Fetch research data separately and organize by object_id in a map
Combine all data into the unified structure
Data Transformation:

Convert database rows to properly typed JavaScript objects
Parse JSON fields (like media formats) into proper objects
Handle null/undefined values appropriately
Ensure all paths are relative (for portability)
Convert absolute media paths to relative /media/ paths
Output:

Write single data.json file to static directory
Minify JSON (no whitespace) to reduce file size
Ensure UTF-8 encoding for international characters
Step 1.4: Implement Media Copy Logic
Create a function that copies the entire project media folder efficiently. The logic should:

Source Identification:

Use existing getProjectMediaPath(projectId) utility to locate source folder
Validate that source folder exists and is readable
Copy Strategy:

Use fs.copy() to recursively copy entire folder structure
Preserve subdirectory structure if any
Copy to src/website/static/media/ during build preparation
Handle large file counts efficiently (avoid loading all into memory)
Path Handling:

Ensure destination paths in JSON match actual file locations
Handle different OS path separators (Windows vs Unix)
Preserve file extensions and naming

Phase 2: Dual-Mode Data Loading
Step 2.1: Create Environment Detection System
Build a reliable method to detect which mode the website is running in:

Detection Logic:

Check for presence of window.api object (exists only in Electron)
Use SvelteKit's browser environment variable
Create isElectronMode constant based on this detection
Why This Works:

In Electron preview: window.api is injected by preload script
In static export: Running in regular browser, no window.api
Detection happens client-side at runtime
alternative: use an environment variable properly set

Step 2.2: Implement Abstracted Data Loader
Create a new module (src/website/src/lib/utils/dataLoader.js) that provides a unified interface for data access regardless of mode:

Interface Design:
The module should export functions like:

loadAllData() - Returns { objects, institutions, researchFields }
getObjectById(id) - Returns single object with all relations
getObjectsByResearchField(rfId) - Returns filtered objects
getObjectsByInstitution(instId) - Returns filtered objects
Implementation Strategy:
Each function should internally branch based on isElectronMode:

Fetch /data.json (with caching), then filter in memory
Caching Strategy:

Cache the fetched JSON in module-level variable after first load

Cache should be shared across all function calls in static mode

Step 2.3: Update Existing Database Utils
Modify dbUtils.js to ensure it returns data in the same structure as the static JSON:

Structure Alignment:

Database query results should match JSON structure exactly
Object records should have embedded institution/researchFields
Media arrays should have same format path structure
This ensures components don't need conditional logic
Backwards Compatibility:

Keep all existing function signatures
Existing preview functionality must not break
Add any new helper functions needed

Phase 3: Static Site Generation
Step 3.1: Configure SvelteKit for Static Adapter
Update svelte.config.js to use @sveltejs/adapter-static:

Adapter Configuration:

Set output directories (pages, assets both to build)
Disable SPA fallback (we want true static pages, not client-side routing)
Enable strict mode to catch prerendering errors
Disable precompression (can be added later if needed)
Prerender Configuration:

Set entries: ['*'] to discover all routes automatically
Configure error handling for missing data
Ensure all routes are discoverable (no dynamic segments without prerendered parents)
Step 3.2: Update Route Loading Functions
Modify all +page.js files to work with static generation:

Enable Prerendering:

Export prerender = true constant
Export ssr = true to enable server-side rendering during build
Load Function Updates:

Use the new dataLoader module instead of direct dbUtils calls
Ensure load functions are async and await data properly
Return data in expected format for components
Static Route Generation:
For dynamic routes like [objId]/+page.js:

Implement entries function that returns all object IDs
This tells SvelteKit which pages to pre-generate
Query data source (via dataLoader) to get list of IDs
Step 3.3: Update Components for Static Compatibility
Review and update all Svelte components to work without client-side navigation:

Component Updates:

Replace goto() with regular <a href> tags where appropriate
Ensure all data comes from data prop passed from load functions
Remove any direct database calls from components
Ensure reactive statements work with static props
Link Handling:

Use SvelteKit's <a> tags with data-sveltekit-preload-data
This enables instant navigation in static mode while preserving prerendered content

Phase 4: Build Execution System
Step 4.1: Create Build Orchestrator
Implement a function that executes the SvelteKit build process programmatically:

Build Process:

Change working directory to website
Execute npm run build command
Capture stdout/stderr for progress reporting
Wait for build completion
Validate that build output exists
Error Handling:

Parse build errors to provide helpful messages
Detect common issues (missing dependencies, syntax errors)
Provide stack traces for debugging
Rollback temporary files on failure
Step 4.2: Implement Post-Build Processing
After successful build, perform cleanup and finalization:

File Organization:

Copy build output from build to final destination
Preserve directory structure
Ensure all assets are included (CSS, JS, images)
Cleanup:

Remove temporary data.json from static
Remove temporary media folder from src/website/static/media/
Clean up any build artifacts that shouldn't be in final package
Validation:

Verify all expected files exist in output
Check that media files are accessible
Validate data.json is included in build output


Configuration Options:

Output directory selection (file picker)


Cancel button for long operations

Result Display:

Success message with output location
Error messages with actionable suggestions
Option to open exported folder

Invocation Flow:

User clicks "Export Website" button
UI validates configuration
UI invokes export service via IPC
On completion, UI shows result
IPC Communication:

Main process handles file system operations
Renderer sends export request
Main sends completion/error events



Missing Data:

Handle objects without media gracefully
Support objects without institutions
Handle empty research fields
Display appropriate placeholders

Verify path handling across OS


The implementation will be considered successful when:

Functional Parity: Static export has identical functionality to preview mode
Performance: Static site loads within 3 seconds on typical broadband
Portability: Exported site works without modification on any static host
Reliability: Export process succeeds consistently for projects of varying sizes
Usability: Export process is intuitive and provides clear feedback
Maintainability: Code is well-documented and follows established patterns
